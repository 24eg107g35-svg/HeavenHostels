# Hostel Management Backend

Spring Boot 4 / Java 21 backend for the existing Heaven Hostels React application. The backend keeps the current frontend wire contracts under `/api/students` and `/api/payments/getpaymentdetails/...`, while also exposing the resource-oriented APIs documented below. Entities are never serialized directly.

## Frontend API audit and compatibility

`frontend/src/api.js` now uses `VITE_API_URL` (default `http://localhost:8080`) and adds the saved Bearer token to protected Axios requests. Public login, registration, refresh, and OTP calls omit that header.

`Register.jsx` exists as a page component but is not currently registered as a route in `frontend/src/App.jsx`; its API contract is still preserved for when that page is routed.

| Page/component | Existing call and request | Response shape consumed | Access |
|---|---|---|---|
| `Login.jsx` | `POST /api/auth/login` `{email,password}` | `{token,role,...}`; `ADMIN` goes to admin dashboard, otherwise student dashboard | Public |
| `Register.jsx` | `POST /api/students/studentregistration` `{StudentRoomNumber,StudentName,email,Role,password}` | Success message; duplicate email has `400` and `"Student already exists"` | Public; student role only |
| `Forgotpassoword.jsx` | `POST /api/auth/send-otp` `{email}`, `POST /api/auth/verify-otp` `{email,otp}`, `POST /api/auth/reset-password` `{email,password}` | `{message}` | Public; rate limited |
| `StudentDashboard.jsx` | `GET /api/students/protected`; then `GET /api/students/getstudentbymail/{email}` | `{user:{email,role}}`; `{data: StudentResponse}` (nullable) | Bearer; own student or admin |
| `StudentFeeManagement.jsx`, `StudentPaymentHistory.jsx` | `GET /api/auth/me`, `GET /api/students/me`, `GET /api/payments/my-history` | Account role, own student profile and `PaymentResponse[]` | Student |
| `StudentDashboard.jsx` | `POST /api/students/addnewstudent` with legacy-cased student profile fields | `{data: StudentResponse}` | Bearer; student can edit their own profile; admin can create/update |
| `AdminDashboard.jsx` | `GET /api/students/allstudents`, `/getbyroomnumber/{room}`, `/unpaidlist`, `/paidlist` | `{data:[StudentResponse,...]}` | Admin |
| `AdminDashboard.jsx` | `PUT /api/students/updatestudent/{id}` with legacy student fields; `DELETE /api/students/deletestudent/{id}` | `{data: StudentResponse}` / `{message}` | Admin |
| `AdminCashPayments.jsx` | `GET /api/students/unpaidlist`; `POST /api/payments` `{studentId,amount,month,year,paymentDate}` | `{data:[StudentResponse,...]}` / `PaymentResponse` | Admin; confirms offline cash |
| `FeeStatus.jsx` | `GET /api/students/paymenthistroy` | `{responses:[{_id,studentName,roomNumber,payments:[...]}]}` | Admin |
| `StudentPaymentHistory.jsx` | `GET /api/payments/{paymentId}/receipt` | Server-generated `application/pdf` blob | Own successful payment or admin |
| `Navbar.jsx` | `POST /api/auth/logout` | `{message}` | Bearer |
| `PaidList.jsx` | `POST /api/students/updatepaymentstatustoUnpaid/{studentId}` | `{message}` | Admin |

Legacy profile fields (`StudentName`, `RoomNumber`, `Sharing`, `Email`, `CollegeName`, `CourseNameandYear`, `Mobilenumber`, `PMobilenumber`, `AmountPerMonth`, `StartingDate`) are accepted, and responses include the same names plus normalized lower-camel fields. Student and payment response IDs include both `id` and `_id`. Payment dates serialize as `yyyy-MM-dd`; statuses preserve the frontend strings (`Paid`, `Unpaid`, `Cancelled`).

The existing admin login was a client-side email/password/token check. It is now a real `/api/auth/login` request and every protected admin API call is authorized from the signed backend role. Public registration only creates student accounts; the former frontend admin secret is no longer an authorization mechanism. Admin accounts are provisioned using the bootstrap environment variables below. The student self-service profile endpoint does not accept a client-claimed room assignment; admins assign rooms through the room APIs. For compatibility with the existing admin Add Student form, its legacy add operation creates an absent room using the selected sharing value as capacity, then assigns the student.

The student receipt UI previously generated its own PDF and hardcoded an amount. It now downloads the PDF generated by the backend from persisted payment and student data.

## API

All successful JSON responses use DTOs. Errors have `{timestamp,status,error,message}` and never expose exception traces.

### Authentication

| Method | Path | Auth | Body/result |
|---|---|---|---|
| POST | `/api/auth/login` | Public | `{email,password}` -> `{token,refreshToken,tokenType,role,email}` |
| POST | `/api/auth/register` | Public | `{email,password,studentName,studentRoomNumber?,role?}` -> `201`; public `role` must be `student` |
| POST | `/api/auth/refresh` | Refresh token | `{refreshToken}` -> rotated access and refresh tokens |
| POST | `/api/auth/logout` | Bearer | Revokes the current access-token version and all refresh tokens |
| GET | `/api/auth/me` | Bearer | `{id,email,role}` |
| POST | `/api/auth/send-otp` | Public | `{email}` -> generic `{message}`; OTP is emailed only for an existing account |
| POST | `/api/auth/verify-otp` | Public | `{email,otp}` -> `{message}` |
| POST | `/api/auth/reset-password` | Public | `{email,password}` -> `{message}`; requires a verified, unexpired OTP |

Tokens are signed HS256 JWTs. Access tokens expire after `JWT_EXPIRATION_MINUTES` (default 30); refresh tokens are random, stored only as hashes, expire after 30 days, and rotate on refresh. Passwords and OTPs are BCrypt-hashed. Public registration cannot create administrators.

| GET / PUT / DELETE | `/api/students/{id}` | Admin; delete deactivates and retains payment history |
| GET | `/api/students/search?q=...` | Admin |
| GET | `/api/students/me` | Student |

| GET | `/api/students/allstudents` | Admin; compatibility `{data:[...]}` |
| GET | `/api/students/getbyroomnumber/{roomNumber}` | Admin; compatibility `{data:[...]}` |

| GET / PUT / DELETE | `/api/rooms/{id}` | Admin |

### Payments and receipts

| Method | Path | Auth |
|---|---|---|
| POST / GET | `/api/payments` | Admin |
| GET / PUT / DELETE | `/api/payments/{id}` | Own student or admin for GET; admin for update/cancel |
| GET | `/api/payments/student/{studentId}` | Own student or admin |
| GET | `/api/payments/my-history` | Student |
| POST | `/api/payments/pay-current` | Student; returns `409` because payments are recorded offline by an administrator |
| POST / GET | `/api/payment-confirmations/mine` | Student; submit and view their offline payment confirmation requests |
| GET | `/api/payment-confirmations/pending`, `/pending/count` | Admin; review requests and display pending request count |
| PATCH | `/api/payment-confirmations/{id}/complete` `{paymentDate}` | Admin; records validated cash payment and completes the request |
| PATCH | `/api/payment-confirmations/{id}/reject` | Admin; rejects a request without marking the fee paid |
| GET | `/api/payments/{id}/receipt` | Own successful payment or admin; PDF |
| GET | `/api/payments/getpaymentdetails/{studentId}` | Own student or admin; legacy response |

Creation example:

```json
{
  "studentId": 12,
  "amount": 6500.00,
  "month": 10,
  "year": 2026,
  "paymentDate": "2026-10-06",
  "transactionId": null
}
```

Payments are recorded offline: after handing over cash, a student may request confirmation from their fee page. The fee remains pending until an administrator reviews the request in `/admin/payment-collection` and confirms receipt; the admin bell displays pending request count. The admin may also record cash directly from the unpaid student list. The entered amount must match the server-stored monthly fee; partial payments are not supported. Students can view their request state (`PENDING`, `COMPLETED`, or `REJECTED`) and payment history. The student must be active; date cannot be future-dated; month/year must be valid; duplicate successful payments and repeated transaction IDs are rejected. A database unique constraint also protects successful-period duplicates. The payment and audit entry commit before the trusted PDF is generated for email and SMTP delivery is attempted. The PDF is attached to the email. A PDF/email failure is logged after commit and never rolls back a successful payment. When the administrator confirms cash, the student receives a notification.

No third-party payment gateway is used. Student self-service online payment is disabled; the legacy `POST /api/payments/pay-current` returns a clear `409 Conflict` explaining that the administrator records offline payments.

### Mess menus, complaints, and notifications

Flyway migration `V2__ai_hostel_data.sql` adds persisted dated mess menus, student complaints, and student notifications.

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/mess/menus/{date}` | Student/Admin | Read the published menu for an ISO date |
| GET | `/api/mess/menus?from=YYYY-MM-DD` | Student/Admin | Read published menus for a seven-day window |
| POST | `/api/mess/menus` | Admin | Create/update a menu by date |
| GET | `/api/complaints/mine` | Student | Read only the authenticated student's complaints |
| POST | `/api/complaints` | Student | Submit a complaint |
| GET | `/api/complaints` | Admin | List complaints with student name, email, room, and ticket ID |
| PATCH | `/api/complaints/{id}/status` | Admin | Change status to `PENDING`, `IN_PROGRESS`, or `RESOLVED` |
| GET | `/api/notifications/mine?unreadOnly=false` | Student | Read only the authenticated student's notifications |
| GET | `/api/notifications/mine/unread-count` | Student | Get the authenticated student's unread notification count |
| PATCH | `/api/notifications/{id}/read` | Student | Mark an owned notification as read |
| POST | `/api/notifications` | Admin | Create a notification for a student ID |
| POST | `/api/notifications/broadcast` | Admin | Persist an announcement for every student account |
| `/api/payment-confirmations/mine` | Student | Submit and track own offline payment request; fee remains pending until admin confirmation |
| `/api/payment-confirmations/pending` | Admin | Review, complete, or reject student payment requests |

The AI reads these stores using the same services and scopes complaint/notification queries by the account resolved from the verified JWT. AI complaint proposals are not persisted until the user confirms the short-lived action token at `POST /api/ai/complaints/confirm`; `POST /api/ai/complaints/cancel` discards a proposal.

The student React screens at `/student/mess-menu`, `/student/raise-complaint`, and `/student/notifications` read and write these persisted records through the APIs above. Students can see each complaint's ticket ID and current status; administrators can review complaints and change status at `/admin/complaints`. A complaint status change also creates a notification for its student. Administrators can send announcements or updates to all student accounts at `/admin/notifications`; students see unread counts on the dashboard and can open and mark notifications read in `/student/notifications`.

### Dashboard

`GET /api/dashboard` (admin) returns `totalStudents`, `activeStudents`, `totalRooms`, `occupiedRooms`, `availableRooms`, `paidThisMonth`, `unpaidThisMonth`, and `revenueThisMonth`.

## Data model and transactions

* `user_accounts` stores normalized unique email, BCrypt password hash, role, enabled flag, and token version.
* `students` has a unique email, optional one-to-one `user_accounts` link, many-to-one `rooms` link, contact/profile fields, and student status.
* `rooms` has a unique room number, capacity, monthly rate, active flag, and one-to-many students.
* `payments` belongs to one student; amounts, period, payment date, status, receipt number, and optional transaction ID are persisted. Unique constraints protect receipt and supplied transaction IDs and a generated MySQL period-status key prevents duplicate `PAID`/`UNPAID` records while allowing multiple cancellation history rows.
* `audit_logs`, `password_reset_otps`, and `refresh_tokens` support audit, password recovery, and token rotation.

Entities have no JSON serialization relationship exposure; endpoints return DTOs. Room assignment/removal, student room updates, payment create/update/cancel, and audit writes run transactionally. Student deletion is soft deactivation to retain financial history.

The initial MySQL schema is in `src/main/resources/db/migration/V1__initial_schema.sql`; Flyway runs it and Hibernate defaults to schema validation.

Source modules are organized under `src/main/java/com/example/backend/{api,api/dto,config,domain,repository,security,service}`. Tests live under `src/test/java/com/example/backend`.

## Configuration and local run

Requirements: Java 21, MySQL 8+, and Maven (the Maven wrapper is included).

Create the database if desired; Flyway creates the tables. In PowerShell:

```powershell
$env:DB_URL = "jdbc:mysql://localhost:3306/hostel_management?createDatabaseIfNotExist=true&serverTimezone=UTC"
$env:DB_USERNAME = "root"
$env:DB_PASSWORD = "<your-local-password>"
$env:JWT_SECRET = "<a-random-secret-at-least-32-characters>"
$env:BOOTSTRAP_ADMIN_EMAIL = "admin@example.com"
$env:BOOTSTRAP_ADMIN_PASSWORD = "<a-unique-password-of-at-least-8-characters>"
$env:CORS_ALLOWED_ORIGINS = "http://localhost:5173"
.\mvnw.cmd spring-boot:run
```

Optional settings:

| Variable | Default | Purpose |
|---|---|---|
| `SERVER_PORT` | `8080` | HTTP port |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | local MySQL defaults | Database connection |
| `DDL_AUTO` | `validate` | Hibernate schema policy; keep `validate` in production |
| `JWT_SECRET` | none (required) | HS256 secret; minimum 32 UTF-8 bytes |
| `JWT_ISSUER` | `hostel-management` | JWT issuer |
| `JWT_EXPIRATION_MINUTES` | `30` | Access token lifetime, allowed 5–1440 |
| `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` | unset | Optional first admin; password minimum 8 characters |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173,http://localhost:5174,http://localhost:5175,http://localhost:3000,http://127.0.0.1:5173,http://127.0.0.1:5174,http://127.0.0.1:5175,http://127.0.0.1:3000,http://localhost:*,http://127.0.0.1:*` | Comma-separated frontend origins or origin patterns |

### AI assistant

For local development, Spring Boot also loads an optional `backend/.env` properties
file when started from the `backend` directory. Put `GEMINI_API_KEY=...` there;
that file is ignored by Git. Alternatively, set `GEMINI_API_KEY` in the backend
process environment before starting the application.

`POST /api/ai/chat` requires an authenticated `STUDENT` bearer token. The request is
`{"message":"What is my room number?","conversationId":null}` and the response is
`{"success":true,"response":"...","conversationId":"...","actionToken":null,"complaintTitle":null,"complaintDescription":null}`. A complaint proposal includes an action token and requires the confirm endpoint described above. Conversation turns are
kept in bounded, user-scoped in-memory sessions for up to 30 minutes. Gemini is
called only from Spring Boot; configure `GEMINI_API_KEY` in the backend deployment
environment and never in the React environment.

The assistant supplies the authenticated student's own profile, room details and
roommates, payment history, date-specific mess menu, complaints, and notifications
as trusted context. It returns a truthful unavailable-menu response when no record
exists for the requested date. The Gemini key remains backend-only.

Do not place production secrets in the React `.env`; provide them to the backend through a secret manager or deployment environment. `BOOTSTRAP_ADMIN_PASSWORD` is read only when no user exists for that email; rotate/remove bootstrap variables after provisioning.

## React connection

Set `VITE_API_URL=http://localhost:8080` in the frontend environment for local development (or the deployed backend origin in production), then run `npm run dev`. The frontend stores the returned access token in `localStorage` to remain compatible with its existing flow. Protected requests attach it as a Bearer token. Configure the backend CORS allowlist to the exact deployed React origin.

## OpenAPI, tests, and deployment

* Swagger UI: `http://localhost:8080/swagger-ui.html`
* OpenAPI document: `http://localhost:8080/v3/api-docs`
* Tests: `.\mvnw.cmd test` (H2-backed; no MySQL or SMTP required)
* Build: `.\mvnw.cmd verify`

For deployment, use TLS, a managed MySQL service, strong externally managed JWT and SMTP secrets, an exact CORS allowlist, database backups, and `DDL_AUTO=validate`. Configure SMTP to enable password recovery and receipt notifications. Request throttling is in-memory and per application instance; use an API gateway or shared limiter for horizontally scaled deployments. Enable only needed actuator/management ports (none are exposed by default), and keep Swagger access restricted if the deployment policy requires it.
